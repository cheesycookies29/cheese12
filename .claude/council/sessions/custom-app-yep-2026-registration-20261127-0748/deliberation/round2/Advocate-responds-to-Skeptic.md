## Advocate Response to Skeptic

**Their position:** Surname + last 4 can be spoofed by a colleague who knows an office line or a business-card number. Skeptic wants one identical reply for every failure (no match, ambiguous, locked out), an activation window from doors-open, per-surname and per-event failure caps, a random status token stored hashed instead of status re-derived from the identifiers, and a repeat self-check-in that flags staff and "does not re-show the seat".

**My response:** Modify.

**Reasoning:** Skeptic and I disagree less than the framing suggests. Skeptic's own Appendix B lists the surname normalisation I asked for (NFKD, diacritics, spaces, hyphens, dots) as P0. My referral-code reply is already a uniform failure reply: "Please see the registration desk and show this code: R-482" looks the same whether the cause is no match, two matches, a lockout or bad input. Skeptic also lists remote spoofing as an accepted residual risk, caught at the door. So I accept most of Skeptic's controls, but each one has to fail *toward the desk*, never toward a dead end. Mrs. Dela Cruz at 6:40 PM must never see a lock screen. If she trips a control, the worst that happens is a visible code and a 20-second desk visit. I concede four things. (1) Every public failure gets the same HTTP status, the same copy, the same layout and similar timing, and differs only in the random referral code. The staff side shows the real reason ("5 wrong last-4 attempts on DELACRUZ"). (2) Normalisation is deterministic canonicalisation only. No fuzzy or edit-distance matching, no first-name fallback and no partial surnames on the public page. Those belong to staff-assisted search behind sign-in. Normalisation folds spelling variants of one surname. It does not merge different people, so it adds no meaningful multi-match. Multi-matches come from shared corporate lines, and they already go to the desk. (3) A 32-byte random status token, stored as SHA-256, is the primary way back to the status page. Re-verifying is only a fallback for a device without the token. (4) The activation window. Before doors open the page says "Registration opens at 6:00 PM". That is event-level information, so it leaks nothing about any guest. I hold firm where a control would strand real guests at peak. **No per-event global lockout.** One script or one crowd of fat-fingered guests could burn a global cap and stop everyone at 6:45 PM. A high global failure rate should *alarm* the Super Administrator, never block. **The per-surname cap must forgive typos.** Count distinct wrong last-4 values, so retrying "4417" three times counts once. Set it at about 5 distinct values per 10 minutes, then route that surname to the desk with the same uniform reply. Any staffer can clear the lock from the referral code in one tap. **On a repeat verification, Skeptic's "do not re-show the seat" protects nothing.** A spoofer sees the table on the first check-in anyway. Hiding it only punishes the real guest who switched phones or lost the tab. My compromise: re-verifying from a device without that guest's token shows the same status, *and* the record gets a "verified again from another device, 6:52 PM" flag in the owner's queue and the Super Administrator's alerts. Detection without scolding. For remote pre-arrival spoofing I would not use the typed rotating desk code: all 300 guests would pay a per-guest typing cost to stop a rare attack. I prefer a zero-typing presence key in the QR URL itself, printed fresh for event day (`/event/yep26?k=…`) and rotatable by the Super Administrator if a photo leaks. I defer to Skeptic and Operator on whether that is P0 or P1.

### Merged guest-verification spec (proposed for convergence)

| Control | Guest sees | Staff see | Fails toward |
|---|---|---|---|
| Normalised exact match (surname or `altSurnames[]` + last 4 of the mobile's digits, or full email) | "Welcome, Ms. Dela Cruz. **Table 3**" / "checked in, choosing your table" | New card in the owner's queue | n/a |
| Any failure (no match, ambiguous, locked, malformed) | One uniform reply: "Please see the registration desk and show this code: R-482" (same status code, layout and timing) | Search pre-filled from R-482, with the real reason shown | Desk, one tap |
| Per-surname cap: about 5 *distinct* wrong last-4 values per 10 minutes | The same uniform reply | "Locked: 5 attempts", with **Clear and check in** | Desk |
| Global failure rate | Nothing changes | Alert to the Super Administrator (for example ">30 failures per 5 minutes") | Never blocks |
| Activation window (doors-open to close; the Super Administrator can open it early or close it) | "Registration opens at 6:00 PM" | Toggle on the dashboard | n/a |
| Status token (32 bytes random, stored SHA-256, scoped to one guest, `no-store`) | The status page shows first name, table, seat and state only | n/a | Re-verify or desk |
| Re-verify from another device | The same status, no error | Flag "verified again from another device, 6:52 PM" | n/a |
| Presence key in the event-day QR URL (P0 or P1, Skeptic and Operator to decide) | Nothing to type | The Super Administrator can rotate the key | Missing or old key gives the uniform desk reply |

**Non-negotiable for me:** no control produces a guest-facing lock screen, "not found", "already checked in" or a different message per failure. Every control ends at the desk with a code that pre-fills the staffer's search.

**Needed from others:** Craftsman, a journey test for each row above, including "locked surname cleared at desk in one action". Tuner, timing parity between the match and failure paths under the single-IP load test.
