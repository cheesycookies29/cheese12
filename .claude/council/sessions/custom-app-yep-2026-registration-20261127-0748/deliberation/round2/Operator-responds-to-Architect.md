## Operator Response to Architect

**Their position:** Keep the event in CORE's shared `db.json` (`caEvents`, `caTables`, `caGuests`, `caLog`). Every `commit()` ends in the synchronous whole-file `db.save()` so validation, change and write happen in one turn of the event loop. A separate data file is considered only if `db.json` grows past about 20 MB, because a second file needs backup, offsite-manifest and restore changes.

**My response:** Modify

**Reasoning:** Architect is right about where the data lives, and I withdraw any suggestion of a second store for this event. I checked the cost of a split. `server/offsite.js:265` refuses any file other than `db.json`, `audit-head.json` and `audit-log.jsonl`. The nightly cron copies only `db.json`. `RESTORE.md` and the nightly restore check know of one data file. A split would therefore change the save path, the cron, the offsite seal, the restore check and the runbook, all in the 12 days before the event, and would give us a recovery path that has never been drilled. That is a worse 3 AM risk than the one it removes. The event also references `db.data.users` for staff roles, so one file keeps a single source of truth with no cross-file consistency to manage.

My objection was never about the file. It is about how finely we can restore. So I accept the shared `db.json` on four conditions, and each one is cheap:

1. **Restore by event, not by file.** An event export/import replaces one event's `ca*` records inside the live `db.json` through one `commit()`-style write and leaves HR, CRM and projects alone. `event.readOnly=true` stays on while it runs. Restoring the whole `db.json` during the event is forbidden in the runbook unless the instance itself is lost.
2. **Event snapshots are derived copies, not a second store.** Every 5 minutes during the event window, an event-only JSON file goes to `data/backups/events/<event>-<HHMM>.json` with its `seq`. The command-desk laptop also pulls it. These files are copies taken from `db.json`, so they need no change to the offsite manifest or the save path. That takes the recovery point from 60 minutes to 5, and to seconds once the `caLog` entries after the snapshot's `seq` are replayed. The same import, given that snapshot, is how we load the warm standby.
3. **The trigger is latency, and it has a date.** Twenty MB is the wrong trigger. What matters is `save()` time on a 1 GB t3.micro while about 300 phones poll. On 28 Nov we measure production's `db.json` size and the `save()` p50 and p95. If the p95 on staging, with production-sized data, is above about 50 ms, we pull the cheap levers first, all before 3 Dec: write compact JSON instead of `JSON.stringify(data, null, 2)` (roughly halves the time and the bytes, and every reader is unaffected), coalesce outbox status writes, and resize to t3.small or t3.medium on 7 Dec. We split only if p95 stays above about 150 ms after that, and that call is made by 30 Nov so the backup and restore changes can be drilled on 6 Dec.
4. **Watch the shared blast radius.** Because a bad write now endangers all of CORE, `commit()` must undo in memory when `save()` throws, as Architect's sketch already does. The event dashboard alerts when `save()` p95 goes above 250 ms or disk free falls below 1 GB. The chaos drill on 6 Dec proves an event restore onto standby in under 5 minutes.

The event snapshots hold guest PII, so they join the retention timer that starts on 10 Dec.
