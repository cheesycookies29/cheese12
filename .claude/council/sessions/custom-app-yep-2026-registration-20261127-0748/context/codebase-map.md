# Codebase map: /home/user/cheese12 (for the CUSTOM APP / YEP 2026 council)

## Project shape
- Two apps in one repo. **CORE ERP** (repo root, "ltdc-erp" v0.70.0-alpha) is where CUSTOM APP goes. **Lancaster ATLAS** (`lms/`, school platform) is separate; ignore it except CLAUDE.md's "keep guides current" rule, which is about ATLAS, not CORE.
- Pure Node (>=18, ESM, `"type":"module"`), **zero npm dependencies** (stdlib only; Playwright only for screenshot/journey scripts). Plain-JS browser SPA, no build step, no framework. `npm start` = `node server.js`; `npm test` = `node --test`.
- Layout: `server.js` (300 lines: HTTP server, static files, security headers, CSP, monitor hook) -> `server/` (API + modules, ~45 files + `dms/`, `mail/`, `pdf/`) -> `shared/` (code imported by BOTH server and browser: roles, modules, per-module constants/validators) -> `public/` (`index.html`, `js/app.js` router, `js/views/*.js` one per module screen, `js/modules.js`, `css/styles.css`, `public/help`, public pages `share.html`, `support.html`) -> `test/` (69 files) -> `deploy/aws` (EC2, Caddy, systemd, backup/offsite/restore timers, `update.sh`, `remote-deploy.sh`) -> `docs/`, `devlogs/`.
- Production: EC2 behind Caddy (HTTPS), single Node process, systemd. Hourly off-server copy plus nightly backups (`server/offsite.js`, `restore-check.js`).

## Request path and API pattern
- `server/api.js` (~1500 lines) `createApi(db, {rateLimits})` returns `handle(req, url, body)`. Routes are registered with `route(method, '/api/x/:id', permission, handler)`; permission is `'public'`, `'auth'`, or a permission string (e.g. `crm.view`) checked via `userCan`. Handlers return plain data or throw `HttpError(status,msg)`. Each module exposes `registerXRoutes(route, db, {audit, files})` (see `server/crm.js:105`, `helpdesk.js`, `projects.js`, `documents.js`, `forms.js`, `assets.js`, `tools-pdf.js`) and is called from `api.js` (imports at top, lines 1-45).
- **Module gating**: `shared/modules.js` has `MODULES` (id, code MOD-nn, glyph, status live/soon), `MODULE_API` (regex per module, e.g. crm = `^/api/crm(/|$)`; non-admins get 403 when the module is switched off in Admin panel), `MODULE_PARTS`, `SWITCHABLE`, `PINNABLE`, `TOOLS` (PDF Studio is the precedent for a non-module "tool"), `INTEGRATIONS`. Adding CUSTOM APP means: a MODULES entry, MODULE_API regex (also cover any `/api/public/<x>` path), MODULE_PARTS text; test `test/modules-roadmap.test.js` and `favorite-modules.test.js` assert module sets.
- **Roles/permissions**: `shared/roles.js` `ROLES` = {label, description, permissions[]}; admin = `['*']`; also `setRoleOverrides` (Admin panel can add/remove per role), `userCan(user, perm)`. Roles: admin, hr, hrstaff, payroll, it, support, sales/salesmgr, etc. A "limited Event staff" type = a new ROLES entry. Per-module access/company roles in `shared/profile.js`.
- **Public (no-login) precedent**: helpdesk public form `/support` + `/api/public/helpdesk` (`server/helpdesk.js:487`, `public/support.html`, `public/js/support.js`): hidden trap field, min fill time, per-IP/email hourly caps, private tracking token link (`/support/t/<token>`). Document share links `/share` + `/api/public/share` (`server/documents.js`, `public/share.html`, `public/js/share.js`; limiter buckets `share-access/-password/-upload`). Rate limiter: `server/ratelimit.js`, buckets defined in `api.js` ~554 (`public-write` 20/h, `api-anon` 120/min, etc.). Page CSP is hash-based for small inline scripts (`server/security.js` `pagePolicy`); a new public HTML page needs to fit that policy.
- Auth: `server/auth.js` (scrypt), sessions in `api.js`, 2-step TOTP (`server/totp.js`, policy in Admin panel -> Sign-in & security), session list/sign-out-others, idle/max-age limits, throttle on failed logins, `scripts/create-admin.js`, `reset-password.js`.
- **No push today**: no SSE/WebSocket anywhere (grep finds none). The browser polls. Live sync would be new server code in raw `http` (server.js owns the response object; `api.handle` returns `{data, headers}` so streaming needs a hook outside `handle`).
- Audit: `server/audit.js` (`createAudit`, `withActor`, `diff`, `mask`, `noAudit`); `audit.js` view; every module records changes. Notifications: `server/notifications.js` (bell, `notify(...)`). Security monitor: `server/monitor.js` counts routes by template, flags signals.
- Email: `server/mail/{smtp,imap,compose,mime}.js`; `sendMail(smtpOptions, {from,to,raw})` and `composeMessage` used by helpdesk (`helpdesk.js` ~261, 794). Credentials encrypted via `server/secrets.js` (key `data/secret.key`). There is **no generic outbox or delivery-status store**; per-message success/failure tracking and resend (spec section 6) must be built. SMTP config lives in helpdesk settings today.
- Files: `server/attachments.js`, `server/dms/*` (encrypted blobs, type sniffing), chunked uploads (`public/js/chunked.js`), CSV helper `shared/csv.js`, xlsx reader in `server/pdf/xlsx-format.js`/office-ooxml (usable for Excel import without deps; verify capability).

## Data model / persistence (the key constraint)
- `server/db.js`: **single JSON file** `data/db.json`, whole object in memory (`db.data`), `db.save()` = `JSON.stringify` the entire dataset, write `.tmp`, `rename` (synchronous, atomic file swap, mode 0600). Back-compat is by `data.x ||= []` for old files plus `emptyData()` for new installs. New module = add collections to `emptyData()` (and `||=` defaults in `openDb`), plus a `migrateX` / `emptyX()` config object as `emptyCrm()`, `emptyHelpdesk()`, `emptyPm()` do (crm.js, helpdesk.js, projects.js).
- Consequence for concurrency: Node is single-threaded and handlers are synchronous against `db.data`, so a synchronous check-then-write (seat count + assign + save) in one handler tick is atomic with no await between; any `await` (email, file IO) between check and write breaks that. Every save rewrites the whole file: ~300 guests plus history is fine, but save frequency at arrival bursts and audit growth should be sized (Tuner). No transactions, no versions/ETags today; optimistic concurrency (per-record `rev`) must be added by the module. Look at `pm`/`crm` handlers for the in-handler validate-then-mutate-then-`db.save()` idiom.
- IDs: `randomUUID()`; human codes via counters in module config (e.g. crm code counters, `HD-000123`).
- Existing collections are flat arrays prefixed per module (`crmDeals`, `pmTasks`, `tickets`, `assets`); follow that (`ca*`/`evt*` prefix) and keep per-event data keyed by eventId.

## Frontend
- `public/js/app.js` is the router: table rows `[path, viewFn, permission, moduleId]` (e.g. `['/crm', crmOverviewView, 'crm.view','crm']`); views in `public/js/views/<module>.js` build DOM with helpers in `ui.js`, `api.js`, `state.js`, `icons.js`; sidebar/launcher in `views/launcher.js` and `modules.js`. Mobile layout guarded by `test/phone-layout.test.js` and `css-balanced.test.js` (style sheet braces must balance; a past release fixed a stray `}`).
- Guest-facing page should be a standalone HTML page like `support.html` (not the SPA) to keep CSP and the master list private.

## Tests and conventions
- `node --test` over `test/*.test.js`. Pattern (see `test/crm.test.js`): `openDb(tmpfile)` + `createApi(db)` and call `handle({method,headers:{cookie}}, new URL(url,'http://localhost'), body)` directly, no HTTP server; helper `client()` keeps a cookie; accounts created via `POST /api/auth/setup` then `POST /api/users`. Concurrency/multi-device scenarios can be simulated by interleaved `handle` calls (all sync-at-core), but real multi-device/load needs a script (`scripts/journeys.mjs` Playwright, output in `journeys-output/`; `scripts/guide-screenshots.mjs`).
- Security tests: `security.test.js`, `vapt*.test.js` (enumeration, headers, rate limits) are the bar a public endpoint must meet; `public-form.test.js` is the closest model.
- Conventions: every release bumps version and adds a devlog entry (`shared/devlog.js` `APP_VERSION`, `devlogs/`, git log style `0.70.0-alpha: ...`); user guides in `docs/guides` and `public/help`; `test/guides.test.js` equivalent for CORE should be checked before adding screens. Comments explain intent at top of each server file; follow that. Commit trailer per session attribution.

## Must-know before proposing changes
1. **The `n8n` and `council` repos are NOT present locally** (`find / -iname '*n8n*'` finds only temp dirs). n8n patterns can only come from the session's own notes or a fetch (github tools are bound to the session repo); say so and mark n8n-derived claims as unverified or from model knowledge.
2. CUSTOM APP = new module in `shared/modules.js` + `server/customapp.js` (`registerCustomAppRoutes`) + `public/js/views/customapp.js` + tests; follow CRM wiring. Keep zero-dependency rule.
3. Atomicity relies on sync handlers; email sends must happen after the save, outside the critical section, with status recorded in a second write.
4. No SSE/push and no outbox exist; both are net-new. Polling with a `since` revision is the cheapest fit.
5. Whole-file JSON save per mutation, shared production instance (other modules' data in the same file): a bug or large write affects all of CORE; recommend a deploy freeze, backup before the event, and consider a separate data file/instance if risk is judged high.
6. Public endpoints need: rate limit bucket, constant-time-ish uniform responses (no enumeration), monitor-friendly route templates, CSP-compatible page, and gating by "registration active" toggle; the master list must never leave via a public route.
7. 12 days to event: prefer reusing CRM/helpdesk patterns over new infrastructure; printable seating plan/guest list as offline fallback.
