# Skeptic (red) — Round 1: Opening perspective

## 1. Opening perspective

ATLAS is well hardened at the HTTP boundary for its age (body schemas, CSRF backstop, rate limits, CSP, scrypt, a fixed VAPT backlog), so my worry is not the front door; it is what sits behind it. For a multi-campus state university, the platform concentrates grades, payroll and the books of account in **one JSON file on one t3.small, one AZ, one admin role and one auto-deploying GitHub branch**: every one of those is a single point of failure, and COA/CSC/CHED/NPC auditors will judge the control environment, not the UI. The pre-mortem I keep landing on is "enrollment week, 2027: the data file outgrew the in-memory/stringify model, saves started failing, memory and disk diverged, and a restart (or a 10-minute auto-update) threw away a day of enlistments and signed out every user". **The most important question from my lens: what is the measured size and save latency of db.json at CBSUA's real scale (students x terms x attendance x submissions x payroll), and what is the cut-over trigger to a real database, before Academic/Finance go live as systems of record?**

Note: the November VAPT (lms/docs/security/VAPT-2026-11.md) tested a local instance only; the live site, AWS account, Caddy/TLS and Keycloak were explicitly out of scope. Treat production as untested.

## 2. Module input

**ATLAS home (/).** Biggest risk: one sign-in opens every system, and there is no native second factor (MFA exists only if Keycloak SSO is switched on, lms/server/sso.js; settings default to password + lockout, lms/server/db.js DEFAULT_SETTINGS.security). One phished admin, registrar, payroll or cashier password reaches grades, payslips and disbursements in one hop. Recommendation: make Keycloak SSO with MFA (or native TOTP) **mandatory** for every admin-side and hris-side account before Academic, People or Finance go live; students/parents can follow later.

**Learn + Admin panel (/lms/, /admin).** Biggest risk: the Admin panel's `data.manage` restore replaces the entire database from an uploaded file in one action by one person (lms/server/api.js `POST /api/admin/restore`, `db.replace`), and the matching backup download is the whole db.json (every student's PII, payroll, ledgers). Academic's `auditLog` and Finance's `finAudit` live inside db.json, so a restore rewrites them too (only audit-log.jsonl survives). Secondary: uploads (10 MB each, `learn.maxUploadMb`) share the 30 GB disk with the data file; a full disk makes `db.save()` throw after the in-memory change was made, so memory and disk silently diverge until the next restart loses the work. Recommendation: in production, restore only from the server console with two people present (or disable the web restore), log backup downloads as a privacy event, put uploads on S3 (or a separate volume) with a disk-space alarm, and fail the request **and roll back the in-memory change** when a save fails.

**Academic (UIS).** Biggest risk: grade integrity has gaps in its maker-checker chain. Grade changes correctly require a different approver (lms/server/academic.js ~L696), but (a) `grade-sheets/:id/approve` does not check that the approver is not the section's teacher, and `post` does not check that the poster is not the approver; (b) `students/:id/credits` (~L533) lets one registrar add a **passed, credited** subject with no second approval; (c) the registrar also holds `academic.settings` (grading scale, passing grade; lms/shared/roles.js L26). A single registrar can therefore manufacture a passing record that feeds a TOR with a valid QR. Recommendation: require a second person (dean or another registrar) for credits and for settings that change grade equivalents, block approve/post by the same person or by the teacher of record, and export a periodic "records created outside grade sheets" report for the Registrar's QA. Migration risk is the other big item: the UIS export (ACADEMIC-PLAN §6 open decision) has no reconciliation plan; require record-count and GWA checksums signed off per campus before cut-over.

**People (HRIS).** Biggest risk: payroll has no checker. The same `hris:payroll.edit` permission creates, adjusts, recomputes and **finalizes** a run (lms/server/hris.js ~L720-748), and HR edits employee bank account and salary grade directly (hris.js L55-58, L90-97) with no approval queue. Ghost-employee and diverted-pay fraud need only HR + payroll, two roles that per-account `access.add` can stack on one person; an administrator can also delete a finalized run if Finance has not obligated it. Self-edit is blocked (VAPT #10 fix), which is good but not enough. Recommendation: add a "reviewed/certified by" step on finalize by a different person, an approval queue (or at least a daily change report to the Chief Accountant) for bank-account and salary-grade changes, and block granting HR and payroll permissions to the same account. Also: DTR geolocation is browser-reported (lms/server/hris-geo.js), so treat it as evidence, not proof, and set a short retention under the Data Privacy Act.

**Finance (FMIS).** Biggest risk: separation of duties is enforced per document but **Administrator = "everything"** (lms/docs/FINANCE-PLAN.md §1 Roles; lms/shared/roles.js `userCan` returns all for admin, and finance-supply.js L345 exempts admins from the own-requisition rule). The DV self-approval check (finance-cash.js L223) is the right pattern but is the exception, not the rule. In a SUC the ATLAS admin is likely an MIS person, who should hold **no** Finance signatory power. Recommendation: remove Finance transactional permissions from the admin role (admin manages accounts only, with that change logged to the hash-chained file), apply the DV-style "not the preparer/certifier" check to ORS Box B, JEV posting, receipts/RCD and period close, and do not go live until FINANCE-PLAN §5 items are signed by the Chief Accountant and, ideally, walked through with the COA resident auditor.

**System (#/system/*).** Biggest risk: the controls live on the box they protect. The hash-chained audit log (lms/server/audit.js) detects edits but sits on the same disk and same Unix account as the app, and its nightly copy goes to the same volume (deploy/aws/ltdc-lms-backup.cron); root or the app account can truncate and rebuild the chain. Recommendation: ship audit-log.jsonl off the box daily (S3 with Object Lock, or CloudWatch Logs) and add an alert on chain breaks and on admin grants of Finance/payroll permissions.

**Facilities (planned).** Biggest risk: a second property register. Finance already keeps PPE and semi-expendable property with depreciation (finProperty/finDepRuns in lms/server/db.js); a Facilities module that also owns "property and equipment" (lms/shared/systems.js L53) will drift from the COA books. Recommendation: Facilities owns rooms, bookings and maintenance only, and reads property from Finance; also settle the overlap with Academic's planned rooms/schedules (ACADEMIC-PLAN phase 3) so one room table exists.

**REX Bookstore e-Reader (planned).** Biggest risk: a third-party commercial vendor receiving student identities and class rosters, with a link the admin can switch live by typing a URL (lms/shared/systems.js L65, `url` setting). That is a personal-data sharing arrangement under RA 10173 and a procurement question for a SUC. Recommendation: no student data leaves ATLAS without a data-sharing agreement, a privacy impact assessment and pseudonymous IDs; integrate via Keycloak/OIDC rather than ATLAS-minted tokens, and keep it "soon" until the vendor's security posture is reviewed.

## 3. Top 3 concerns (ranked)

1. **Critical — the single-JSON-file datastore will not survive CBSUA scale, and it fails unsafely.** Evidence: lms/server/db.js `save()` does a synchronous `JSON.stringify(data, null, 2)` of the whole dataset plus a full rewrite on every change; the demo school is ~4.8 MB with about 130 students (lms/server/demo.js PLAN). A rough linear extrapolation to tens of thousands of students and several years of attendance, submissions and payroll lands in the hundreds of MB: multi-second event-loop stalls on each save at peak, memory pressure on a 2 GB t3.small, and a hard V8 string-length ceiling (~512 M chars) beyond which `save()` throws. When it throws, the in-memory change stays and the disk does not, so data is lost at the next restart or auto-update. Mitigation: benchmark with a synthetic CBSUA-sized dataset now; set a cut-over trigger (e.g. 50 MB or 200 ms save) to SQLite/PostgreSQL per collection (the comment at the top of db.js already anticipates it); until then, roll back memory on save failure and alarm on save latency.

2. **High — change management and availability rest on a personal working branch and one box.** Evidence: lms/deploy/aws/EC2.md "Updates": production pulls the `claude/compassionate-edison-kc7gd0` branch every 10 minutes and runs whatever passes the tests ("anyone who can push to that branch can change what your school's server runs"); sessions are in memory (lms/server/auth.js L241), so each auto-update signs everyone out mid-quiz or mid-grade-entry; nightly backups sit on the same disk (lms/deploy/aws/ltdc-lms-backup.cron) and the only off-box copy is 7 days of same-account snapshots, far short of COA records retention; the address is a free DuckDNS name controlled by one token. Mitigation: release tags from a protected, CBSUA-owned repo with two-person review; deploy windows (never during enrollment or grade-posting weeks); persist sessions (or drain before restart); cross-account/off-site backups with long retention and a tested restore drill; a cbsua.edu.ph hostname; a written RTO/RPO and a standby instance or at least a documented rebuild. Also re-decide cloud (Singapore) versus the on-premise option against DICT/NPC guidance for a SUC.

3. **High — separation of duties is incomplete exactly where fraud happens: payroll, grade crediting, and the all-powerful admin.** Evidence: payroll finalize by the same permission that edits (lms/server/hris.js ~L740); bank/salary edits without approval (hris.js L55-97); credited passed subjects with one approver (lms/server/academic.js ~L533); grade-sheet approve/post without a different-person check (academic.js ~L617, ~L637); admin holds every Finance power and is exempt from the requisition rule (FINANCE-PLAN.md §1, finance-supply.js L345); single-person whole-database restore (api.js L456). Mitigation: a maker-checker rule on every step that creates value (money or credits), an admin role that administers accounts but cannot transact, a conflicting-permission matrix enforced when access is granted, and exception reports (credits, bank-account changes, finalized-run deletions, restores) reviewed by someone outside IT.

Calibration: I am not calling for a rewrite. Learn as an LMS can go live on the current stack with MFA for staff and a deploy freeze calendar. Academic, People payroll and Finance should not become the **system of record** until concern 1 is measured and concern 3's maker-checker gaps are closed.
