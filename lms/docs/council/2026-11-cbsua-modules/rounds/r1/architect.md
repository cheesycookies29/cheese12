# Architect (blue) — Round 1: Opening perspectives — CBSUA modules

## 1. Opening perspective

ATLAS is a well-disciplined modular monolith: one process, one route table (`server/api.js` `route(method, pattern, access, handler)`), module boundaries expressed as URL prefixes and permission strings, and cross-module calls that go *through the route layer* (`ctx.invoke`, used by the home figures in `server/api.js:564-600` and payroll-to-Finance in `server/hris-finance.js`), which is exactly the right integration pattern for a monolith that may later split. The weak point is not the module design but the **persistence and runtime substrate**: `server/db.js:206-210` serialises the *entire* database with `JSON.stringify(data, null, 2)` + `writeFileSync` on every one of ~249 `db.save()` call sites, and sessions live only in process memory (`server/auth.js` `createSessions`) on a box that auto-restarts on every GitHub push (`deploy/aws/update.sh:68-73`). I measured the demo school: 203 students, 38 employees, 4.48 MB pretty JSON, 17 ms per stringify; ~75% of bytes are per-student collections (`attempts`, `enrollments`, `submissions`, `attendance`, `users`). Linear extrapolation to ~15–25k students gives ~350–600 MB per year of operation, i.e. multi-second event-loop stalls per write and, past ~512 MB, a hard V8 string-length failure in `JSON.stringify`. **The most important question from my lens: what is the storage engine and the system of record for each entity *before* CBSUA data is imported, because the import is the point after which every migration gets expensive?**

## 2. Module input

**ATLAS home (`/`, `shared/systems.js`, `server/api.js` `figuresFor`).** Live figures are computed by fanning out to each system's own routes via `ctx.invoke`, so permissions and campus rules are reused rather than duplicated — good contract hygiene. The cost is that every home load re-runs full dashboards (`/api/home`, `/api/academic/dashboard`, enrollment summary), each a linear scan over in-memory arrays (no persistent indexes: `Map` is only used locally; 17 `enrollments.filter` scans in `server/`). Recommendation: keep the invoke pattern, but cache each figure per user for 30–60 s and add in-memory secondary indexes (by `studentId`, `sectionId`, `campusId`) maintained on write, so the enrollment-week login spike does not multiply into N full scans per page view.

**Learn + Admin panel (`/lms/`, `/admin`; `server/classroom.js`, `quiz.js`, `attendance.js`, `enrollment.js`, `files.js`).** This is the write-hot, high-cardinality module: quiz attempts (~940 B each), submissions, attendance (one record per section per date) and enrollments dominate the data file, and uploads arrive as base64 inside JSON up to 20 MB (`server.js` `readBody`, `server/files.js:2,40`), which is parsed on the single event loop. `docs/ACADEMIC-PLAN.md §3.1` already says Academic becomes the system of record for sections/enrollment and Learn consumes them, but both still mutate the same `sections`/`enrollments` arrays directly. Recommendation: write down ownership now (Academic owns `sections`, `enrollments`, final grades; Learn owns lessons/assignments/attempts/attendance and *reads* rosters), and move uploads to a streamed binary endpoint (raw body to `data/files/<id>`, metadata in JSON) before quiz/exam season.

**Academic (`/academic/`, `server/academic.js`, `docs/ACADEMIC-PLAN.md`).** The grade-sheet state machine (submitted → approved → posted, `academic.js:581-660`) and immutable `academicRecords` with `gradeChanges` are the right shapes for a registrar system, and campus scoping is applied per query (`campusId` filters at 433, 586, 733). Two contract gaps: the plan's §3.3 adds `registrations`, `assessments`, `payments`, while Finance already has `finReceipts` with a `studentId` link (`server/finance-cash.js:476-500`) — that is two payment ledgers waiting to happen; and the plan text still says "ATLAS Finance, coming soon" though Finance is built (doc drift). Recommendation: resolve open decision §6.7 now as **Academic owns the assessment (what is owed), Finance owns the O.R./receipt (what was paid)**, with Academic reading paid status via `ctx.invoke` on a Finance route, and no `payments` collection in Academic.

**People (`/hris/`, `server/hris*.js`).** The payroll → ORS → DV → remittance bridge (`server/hris-finance.js:1-14`) correctly goes through Finance's own routes so allotment, numbering, period-lock and separation-of-duties rules apply — the best integration in the codebase. Weak seam: payee cards are found **by case-insensitive name** (`cardFor`, `hris-finance.js:124-126`), so renaming a card or a campus silently creates a duplicate payee and splits the subsidiary ledger. Recommendation: persist the card id on `hrSettings.gov` per campus/agency (stable foreign key, name only as display), and treat `employees` ↔ `users` (`user.employeeId`) ↔ `finCards.userId` as one documented identity chain with a uniqueness check at each link.

**Finance (`/finance/`, `server/finance*.js`, ~123 routes).** COA/DBM rules are encoded centrally (`fx.post` journal posting, period lock, numbering via `finCounters`), and the fact that every money document ends in a JEV gives a single ledger — structurally sound. It is the module least tolerant of the JSON-file substrate: a lost write between the nightly copy and a crash is a missing O.R. number or JEV, which is an audit finding, and `update.sh:64` copies `db.json` *before* stopping the service, so a rollback can drop writes made in that window. Finance is also not campus-scoped beyond users (correct for one SUC accounting entity, but collecting officers per campus need RCD scoping). Recommendation: Finance must not go live on CBSUA books until persistence is per-record and durable (see concern 1); meanwhile clear `docs/FINANCE-PLAN.md §5` items with the CBSUA accountant and add a per-campus collector/RCD filter.

**System (`#/system/*`, `server/system.js`, `audit.js`, `monitor.js`, `sso.js`, `cloudflare.js`).** The hash-chained append-only `audit-log.jsonl` (`server/audit.js:5-9`) is the right design and correctly lives outside `db.json`; but Academic (`data.auditLog`, `academic.js:56`) and Finance (`data.finAudit`, `finance.js:101`) keep their own logs *inside* the rewritable data file, merged only at read time. Recommendation: route `academic` and `finance` audit events into the hash-chained log (keep the in-file arrays only as a denormalised view or drop them), so grade changes and voucher approvals get the same tamper evidence as sign-ins — that is what COA and CHED auditors will ask about.

**Facilities (planned; `shared/systems.js` tile only, 0 routes).** Three modules already hold fragments of its domain: `sections.room` is free text, `ACADEMIC-PLAN.md §3.3` plans rooms/exam venues for the Scheduler, and Finance has `finProperty`/depreciation. Recommendation: define one `rooms` entity (campus, building, code, capacity, type) *now*, owned by Facilities but created early for Academic scheduling, referenced by id from sections and exam schedules; Facilities property views should reference `finProperty` (Finance stays the book of record), not copy it.

**REX Bookstore e-Reader (planned; external).** This is an integration, not a module: the boundary should be identity + roster + entitlement, never content in ATLAS. Recommendation: ATLAS issues the identity (Keycloak/OIDC already in `server/sso.js`), exposes a narrow read-only roster contract (section → enrolled student ids, course code → ISBN mapping held in ATLAS), and launches into REX via signed deep link or LTI 1.3; no e-book bytes or REX tokens in `db.json`, and the outbound call goes through `ctx`-style adapters with a timeout so a REX outage never blocks a class page.

## 3. Top 3 concerns (ranked)

1. **Whole-file JSON persistence will not survive CBSUA scale or Finance's durability needs.**
   Evidence: `server/db.js:206-210` (full `JSON.stringify(...,null,2)` + `writeFileSync` per save, ~249 call sites); measured 4.48 MB / 17 ms for 203 students; ~75% of bytes scale per student, so ~100x students means ~1.5–2 s of blocked event loop per write and a heap of 1–2 GB on a 2 GB t3.small, with a hard ceiling at V8's ~512 MB string limit. Writes are not fsync'd and backups (`data/backups/`) sit on the same EBS volume. Proposed path, keeping the zero-dependency rule: keep arrays in memory as the read model, but persist **per record** to `node:sqlite` (built into Node 22.13+/24, so no npm dependency; WAL, one table `docs(collection,id,json)` matching the "one table per collection" note in `db.js:2-3`), driven by an explicit `db.touch(collection, record)` or dirty-collection flag at the existing `save()` sites. Do this before the UIS import (`ACADEMIC-PLAN.md §6.6`); PostgreSQL/RDS remains the later step `docs/BENCHMARK.md §4.6` already names.

2. **In-memory sessions + auto-deploy-on-push + scrypt throughput = enrollment-week outage.**
   Evidence: sessions only in memory (`auth.js` `createSessions`); `update.sh` stops and restarts the service on every new commit to a branch, within 10 minutes, at any hour; scrypt is limited to `HASH_SLOTS = 2`, `HASH_QUEUE = 100` at ~0.3 s each (`auth.js:84-114`), i.e. roughly 6–7 local sign-ins/second. A restart during enrollment signs out ~15k students, and the re-login wave hits 503 "busy" for tens of minutes. Recommendation: persist sessions (hashed token → session row, same SQLite file), switch production to a release channel (tagged releases, deploy window, freeze during enrollment and grade-posting weeks), and make Keycloak SSO the default for students so password hashing is not on ATLAS's two thread-pool slots.

3. **System-of-record ambiguity across modules before the CBSUA data lands.**
   Evidence: Learn and Academic both mutate `sections`/`enrollments`; Academic plans `payments` while Finance has `finReceipts.studentId` (`finance-cash.js:476-500`); rooms are free text in `sections` and planned again in Academic and Facilities; payee cards matched by name (`hris-finance.js:124`); three audit stores (`audit-log.jsonl`, `auditLog`, `finAudit`); schema migrations happen implicitly in `normalize()` with `version: 1` never bumped (`db.js` `emptyData`, `normalize`), so a rollback after a shape change has no version check. Recommendation: a one-page ownership map (entity → owning module → who may read/write → contract route), a monotonically increasing schema version with explicit migrations, and id-based links everywhere a name is used today.
