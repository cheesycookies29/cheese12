FROM: Architect
A: Do not split a request's write set across two stores. During the hybrid period, the remaining db.json becomes one row (kv 'legacy', a JSON blob) inside the same SQLite file. Each request then commits its moved rows and the legacy blob in one BEGIN/COMMIT. Measured: 19.5 ms for 1 row plus a 5 MB blob, against 0.19 ms for a durable 2-row transaction. A failed commit triggers ROLLBACK and restores the in-memory snapshot, so memory and disk cannot diverge. Migrate by write-set cluster, not by single collection. auditLog moves first, since almost every route appends to it. Then Learn (attempts, submissions, attendance). Then sections, enrollments, academicRecords and gradeSheets together. Then all fin* collections in one step, so SQLite transactions replace finSnap. On memory, in-memory Map indexes stay only for the bounded hot set: current-term sections, about 100k enrollments, and seat counts. academicRecords with alumni history never live in the heap: 2M records (a 1.6 GB file) ran at 123 MB RSS, and a per-student lookup on (studentId, termId) took 0.035 ms. So prerequisite checks load one student's passed-course Set per request instead of keeping a global Map.
FOLLOW-UP (optional): Will you accept "legacy JSON blob inside the same SQLite file" as the hybrid atomicity mechanism? It costs about 7 ms per MB of what remains in db.json for each write. If yes, should the merge gate require db.json to stay under 20 MB, keeping that cost under about 140 ms?
