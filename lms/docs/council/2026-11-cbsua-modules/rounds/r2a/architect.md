FROM: Operator
A: There will be no hybrid period across two stores. I withdraw the collection-by-collection move. In one offline cut-over, every collection, including `finCounters`, `counters` and settings, goes into a single SQLite file. After that, db.json is only read once and kept read-only as the rollback artifact. A point-in-time backup is then one file and one snapshot ID: `node:sqlite`'s `backup()` or `VACUUM INTO`, both checked here on Node 22.23.4. It can never pair new `finReceipts` with an old `finCounters`, because both are written in the same `BEGIN IMMEDIATE…COMMIT`. A boot check also refuses Finance writes if any series counter is lower than the highest number already issued. `update.sh` changes in three ways. It must stop the service before taking the snapshot: today line 64 copies before `systemctl stop` (line 68), and a plain `cp` of a live WAL database is not consistent. The nightly `cp db.json` cron becomes `backup()` plus an hourly upload to S3. The hash-chained `audit-log.jsonl` and the write-once `data/files/<id>` are never restored backwards: a restore adds a "data restored to snapshot X" audit entry.

FROM: Skeptic
A: For the bounded, in-memory collections, I replace "remember to `touch`" with a checked contract. A bare `save()` becomes a test failure, enforced by grep in `npm test` like `guides.test.js`. Every save names what it changed, as `save('sections','auditLog')` or `touch('users', u)`, and only records whose serialised form changed are written. The test database also compares the whole dataset before and after every route test and fails if an unnamed collection changed. In production, a background reconciler (chunked, every 5 minutes, and always at SIGTERM before a deploy restart) compares memory with SQLite, writes any difference and raises an alert naming the collection and the last route. A missed name therefore costs at most 5 minutes, and only after a crash, and it is reported instead of silent. Collections moved out of the heap (see Tuner) cannot diverge, because there the SQL write is the mutation. The cut-over is proven offline: per collection, the record count and the SHA-256 of the canonical, id-sorted JSON must match between db.json and a read-back from SQLite. If any differ, the switch does not happen, and the report is kept with the backup. On stability: `node:sqlite` has been unflagged since 22.13 but is still Stability 1.1 and prints an ExperimentalWarning (bundled SQLite 3.53.4 here). The risk is the JS API, not the file format, which any `sqlite3` tool can read. So the store sits behind one ~100-line adapter using only `DatabaseSync`/`prepare`/`exec`/`backup`, with a startup self-test (write, read, `quick_check`). Node is held at its current 22.x until tested, because today unattended-upgrades updates NodeSource Node under the running app without running `update.sh`'s tests.
FOLLOW-UP (optional): Is a ≤5-minute, alerting, crash-only loss window for a mis-declared write "loud enough"? Or do you need the request itself to fail? That needs a per-request full diff, which costs about 30–100 ms per write at CBSUA scale.

FROM: Tuner
A: The rule is that a collection leaves the heap if it grows per student per term or per day, and stays if it is bounded by the size of the catalog or staff. Out of the heap, queried on demand through indexed repository functions: `academicRecords` (studentId, termId), `issuedDocuments`, `attempts` and `submissions` (assignmentId, studentId), `attendance` (sectionId, date), `timeEntries` (employeeId, date), payslips split out of `payrollRuns`, `auditLog`, `finAudit`, `settingsLog`, sessions, and enrollments for closed terms. In the heap, with Map indexes kept up to date on write: settings, campuses, users, programs, courses, terms, curricula, sections, open-term enrollments, `fin*` master and document collections, and employees. Target: under about 300 MB with `--max-old-space-size=1024` on the t3.small. The UIS import writes straight into the `academicRecords` table and never passes through the heap or JSON. A forgotten `touch` is caught by the named-save contract, the strict test database and the reconciler described to Skeptic. It cannot happen for the out-of-heap collections. I also found that today's `finSnap` (`api.js:807-816`) is not safe either. It restores the snapshot taken before the handler's `await`. `POST /api/finance/users` checks the fields again after the scrypt wait (`finance.js:442-443`), so a failure there wipes any OR or JEV that another request committed during that wait. The new unit of work must therefore collect writes and commit them synchronously after the handler. It must not hold a transaction or snapshot across an `await`.

REVISED PLAN:
- **One store, one cut-over, no hybrid:** an offline migration moves every collection into a single WAL-mode `node:sqlite` file, proven by per-collection count and SHA-256 checks. db.json stays read-only as the rollback artifact and is never written again. This must happen before the UIS import, and before W1 if W1 brings real CBSUA quiz or attendance volume.
- **Two tiers:** bounded collections stay in memory (Map indexes) and are saved by named-collection diff. Unbounded per-student and per-day collections live only in SQLite behind indexed repository functions, and the UIS import goes straight into those tables.
- **Unit of work replaces `finSnap`:** each request's writes, and the writes of the HRIS purge and monitor timers, are collected and committed in one synchronous `BEGIN IMMEDIATE…COMMIT` after the handler, never across an `await`. On error, the transaction rolls back and the named collections are reloaded from SQLite.
- **Safety nets:** a bare `save()` fails `npm test`; a strict test database diffs the whole dataset per route test; a background reconciler plus a flush at SIGTERM; a boot check that each counter is at least the highest number issued; `PRAGMA user_version`, so older code refuses a newer schema.
- **Ops:** `update.sh` stops the service and then calls `backup()` (one snapshot ID). The nightly `cp` becomes `backup()` plus an hourly S3 upload (Operator's RPO). The audit log and uploaded files are never rolled back. Node is held at its current 22.x behind a store adapter with a startup self-test.
