# ATLAS vulnerability assessment and penetration test: November 2026

**Scope:** Lancaster ATLAS (`lms/`): the HTTP server, the API (all apps: home, Learn and its admin panel, People, Academic, Finance, Help) and the browser apps.
**Target:** a local instance of the same code that is deployed (the branch `claude/compassionate-edison-kc7gd0`), with the demo school loaded. The live site, its AWS account, Caddy's TLS set-up and Keycloak were **not** tested.
**Method:**
- A code review of access control (every route and who may call it) and of injection and XSS (every place the apps write HTML, CSV and calendar files).
- Live probes with raw HTTP requests:
  - malformed addresses, Host headers and bodies;
  - path traversal and oversized uploads;
  - slow headers and request floods;
  - CSRF-style requests;
  - password guessing and timing.
- An XSS fuzz crawl: a script payload was placed in about 9,400 text fields of the demo school, and about 660 screens were opened as admin, registrar, teacher, student and parent.
- Each finding below was reproduced, then retested after its fix. `test/security.test.js` keeps them fixed.

## Findings

| # | Severity | Finding | Status |
| --- | --- | --- | --- |
| 1 | **Critical** | One request with a malformed address (`GET /%E0%A4%A`) or a malformed `Host` header stopped the whole server, with no sign-in needed. Everyone was signed out (sessions live in memory), and repeating it kept the site down. | Fixed |
| 2 | **High** | Stored XSS from the public application form: an applicant's name with HTML ran as script for the Finance cashier who looked the student up when issuing a receipt (`finance/views/revenue.js`). | Fixed |
| 3 | **High** | An HR manager could create Finance office accounts (Approving Officer, Cashier…) with a password of their choosing, and re-password or retype existing ones. One person could hold every signature on a disbursement voucher. | Fixed: administrators only |
| 4 | **High** | No rate limiting beyond a per-username lock. A script could flood the API, guess passwords across many usernames (password spraying), or tie up the server with slow password checks. | Fixed: rate limiter (below) |
| 5 | **Medium** | Account lock-out could be abused: five wrong passwords from anywhere locked a username for everyone, so a stranger could lock the administrator out. The applications pause was also global: one script stopped every applicant for 5 minutes, and a wrong setup code blocked the real administrator too. | Fixed: per address |
| 6 | **Medium** | Registrars and admins received every user's private calendar address (`calendarToken`) and Keycloak link in user lists. The calendar address opens a person's calendar without signing in. | Fixed |
| 7 | **Medium** | No Content-Security-Policy, so any XSS could run freely. | Fixed: strict CSP, no inline scripts except the dark-mode snippet (by hash) |
| 8 | **Medium** | CSV formula injection: exported names starting with `=`, `+`, `-` or `@` run as formulas in Excel or Sheets. A public applicant controls their name. | Fixed |
| 9 | **Medium** | An upload over 20 MB was refused but still read to the end and kept in memory. Bytes were also joined as text per packet, which could break letters such as ñ split across packets. | Fixed |
| 10 | **Low** | Officers could change their own leave credits, leave adjustments and HR record (pay rate), and payroll officers could adjust their own payslip. | Fixed: another officer or an admin does it |
| 11 | **Low** | Parents and guardians could open People (HR settings, leave types). | Fixed |
| 12 | **Low** | Slow-header connections ("slowloris") were held open for up to 60 seconds. | Fixed: 20 seconds |
| 13 | **Low** | A lone carriage return in a title could add properties to the iCalendar feed. | Fixed |
| 14 | **Low** | Keycloak sign-in matched accounts by an email whose `email_verified` claim was missing. | Fixed: must be `true` |
| 15 | **Low** | `//other-site` was accepted as an ATLAS address in guides and in Home page & systems (admin-only open redirect). Bold markers inside a link address in guides produced broken markup. | Fixed |
| 16 | **Low** | Program and campus names on the application form were only partly escaped (admin-set). | Fixed |
| 17 | **Info** | The `X-Frame-Options: DENY` header also blocked ATLAS's own PDF previews. | Changed to `SAMEORIGIN`, with `frame-ancestors 'self'` |
| 18 | **Info** | Expired sessions and failed-sign-in records stayed in memory until used again. | Fixed: swept periodically |
| 19 | **Info** | A JSON body of `null` caused a server error (500). | Fixed: 400 |

### Checked and found sound

- **Classes and their contents:**
  - Teachers reach only their own sections.
  - Students reach only their own work and grades.
  - Parents reach only linked students, as far as each link allows.
  - Every id is checked against its class first.
- **Scoping across systems:**
  - Campus scoping holds in Learn, Academic, People and Finance.
  - Finance has separation of duties: whoever prepares or certifies a voucher cannot approve it.
  - Role overrides are admin-only.
- **Public routes:**
  - `/api/auth/apply` takes only the fields it expects and creates a student awaiting review.
  - First-run setup works only once and checks the setup code in constant time.
  - Document verification shows masked details.
  - Calendar feeds need a 192-bit token.
- **Uploads:**
  - Only PDFs, images, audio and video are shown in the browser; everything else is downloaded.
  - Files are sent with `nosniff` and a sandboxing CSP.
  - Files are stored by random id, so there is no path traversal.
  - SVG and HTML cannot be served from ATLAS's address.
- **Requests and sessions:**
  - Path traversal (`..`, encoded slashes and backslashes, null bytes) is blocked.
  - CSRF is prevented by cookies with `SameSite=Strict` and `HttpOnly` (`Secure` in production), JSON-only request bodies, and the `Host` check.
  - Session tokens are 256-bit random values, and other sessions end when a password changes.
  - Passwords are hashed with scrypt, and the check takes the same time whether or not a username exists.
- **Code:** there is no `eval`, no shell commands built from input, and no prototype pollution.

## The rate limiter

`server/ratelimit.js`, wired in `server/api.js`. It needs no dependencies, keeps a sliding window per key in memory, has a bounded number of keys, and answers `429 Too Many Requests` with `Retry-After`.

| Limit | Default | Counted per |
| --- | --- | --- |
| Any API request, signed in | 300 a minute (**Settings → Sign-in and passwords**, 60–3000) | person |
| Any API request, signed out | 4 × the above (a whole school may share one address) | network address |
| Sign-in attempts | 60 a minute | address |
| Wrong passwords, any usernames | 30 in 15 minutes (**Settings**, 10–1000) | address |
| Wrong passwords for one username | the lock-out setting (normally 5), then that username is locked for that address only; 10 × as many lock it everywhere | username + address |
| Password changes | 10 in 15 minutes | person |
| Applications for admission | 10 an hour | address |
| First-administrator setup | 20 in 15 minutes | address |
| Document checks, calendar feeds, Keycloak sign-ins | 60 a minute | address |

The address is the connection's own address. Behind Caddy, it is the last entry of `X-Forwarded-For`, which is believed only when the connection comes from this computer. `RATE_LIMITS=off` turns the limiter off for load tests.

## Remaining risks and recommendations

1. **Test the live site's infrastructure** with the owner's go-ahead. That means:
   - the TLS set-up (Caddy issues HTTPS; HSTS is on);
   - the AWS security group, which should allow only ports 80 and 443 (SSH via Session Manager);
   - the DuckDNS token's storage;
   - the backup bucket's permissions;
   - Keycloak's realm settings.
2. **One process holds everything in memory**: sessions, rate-limit counts and the JSON database. A restart signs everyone out, and counts are per process. Running more than one server needs a shared store (see README, "When one server is no longer enough").
3. The server now logs unexpected errors and keeps running rather than stopping. Watch the service log (`journalctl -u ltdc-lms`) for "Unexpected error" lines and report them.
4. **Passwords**:
   - consider at least 10 characters and **Passwords mix letters and digits**;
   - single sign-on with Keycloak gives multi-factor sign-in;
   - ATLAS itself has no second factor yet.
5. **There is no sign-in audit log** (who signed in, from where, failed attempts). Worth adding for the administrator.
6. **Downloads hold the whole database.** The admin panel's **Demo data & backup** download contains every account, including password hashes. Keep such files encrypted and off shared drives.
7. **Tune the limits** if a campus shares one internet address: raise **Wrong passwords per network address** first.

## Retesting

```bash
cd lms && node --test test/security.test.js
```

The tests cover each fix above. The probe scripts used for this report (malformed requests, floods, slow headers, the browser CSP check) were run against a throw-away local server and are not part of the repository.
