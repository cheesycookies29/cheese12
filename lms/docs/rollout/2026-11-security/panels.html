The path of every request

Eight checks before anything reaches your data.

A request that fails a check is turned away with a clear answer, and the server keeps running for everyone else. Nothing below is an add-on: each check is part of ATLAS itself, or of the server it runs on.

1HTTPS onlyCaddy

Every connection is encrypted, and browsers are told never to use plain HTTP for a year (HSTS).

Eavesdropping on shared Wi-Fi
2Address checkServer

Requests must be addressed to the school's own ATLAS address. Malformed ones get a plain "400" and go no further.

Host-header tricks, crash attempts
3Rate limitsServer

Each person and each network address has a budget per minute; past it, the answer is "429, try again in a moment".

Floods, password-guessing scripts
4Same-site onlyServer & browser

Changes are accepted only as JSON from ATLAS's own pages; the sign-in cookie is never sent with another site's request.

Cross-site request forgery
5SessionSign-in

A 256-bit random token in a cookie that page scripts cannot read. Idle sessions end on their own (after 8 hours by default).

Guessed or borrowed sessions
6Role & permissionEvery route

Each of ATLAS's 400 API routes states who may call it, and is checked against the account's role and permissions.

Doing what your role cannot
7ScopeCampus, class, family

Staff see their own campus, teachers their own sections, students their own work, parents only their linked children.

Seeing other people's records
8Business rulesSeparation of duties

Whoever prepares or certifies a voucher cannot approve it; officers cannot change their own pay, leave or attendance.

One person controlling a transaction
Your school's recordsChanged only by a request that passed all eight, with an audit trail of who changed what, and when.

Layer 3 · The rate limiter

A limit on every door.

ATLAS counts requests in a sliding window, per person when signed in and per network address when not. Sign-in, applications and lookups each have a tighter limit of their own. It is built into the server: no extra service to run.

Layer 5 · Passwords and sign-in

Passwords that are no use to a thief.

ATLAS never stores a password. It keeps a one-way scrypt hash, and then locks that hash with AES-256-GCM under a key kept apart from the data.

Typed

The password

••••••••••

Step 1 · scrypt

Hashed one way

Salted and deliberately slow, so guessing it costs time; it cannot be turned back into the password.

Step 2 · AES-256-GCM

Then encrypted

With a key the server keeps outside the data: in its settings or a file only ATLAS can read.

Stored

enc1$k1$Qm9v…$c2Vh…

All the data file ever holds.

A copy of the data on its own holds no hashes to crack: the key is not in it. Keys can be changed without anyone resetting a password.

ATLAS sign-in

  • Session cookies are HttpOnly, SameSite=Strict and Secure
  • The same answer, in the same time, whether or not a username exists
  • A password change ends every other session of that account
  • Administrators set the length and mix of passwords, and the lock-out

Optional · Keycloak single sign-on

  • OpenID Connect with PKCE, state and nonce
  • The server checks each token's signature, issuer, audience and expiry
  • Accounts link only by a verified email; the client secret stays on the server
  • The school's own Keycloak rules apply, including two-step sign-in where it is on

The server · Amazon Web Services

A locked-down server.

ATLAS runs on one Amazon EC2 server set up from a single CloudFormation template, so every school's server is set up the same way.

Network

Security group

  • Only ports 80 and 443 are open
  • No SSH: administrators connect through AWS Session Manager

Disk & data

Encrypted EBS

  • The whole disk is encrypted
  • The data folder and password key are closed to other accounts

Instance

Ubuntu 24.04 LTS

  • Automatic security updates, Node.js included
  • Instance metadata requires IMDSv2 tokens

Service

systemd sandbox

  • Runs as its own account, never as root
  • The rest of the system is read-only to it; it writes only to its data folder

Updates

Tested before installed

  • Every test runs first, as an unprivileged account with no network
  • Installed only if all pass; otherwise the old version stays

Backups

Two kinds

  • A copy of the data every night, kept 30 days
  • A snapshot of the whole disk every day, the last 7 kept
Caddy: automatic HTTPS certificates Secrets in the server's settings, never in the code Or one computer on the school's own network

The framework and the backend

Built on the standard library.

ATLAS uses no web framework and no outside packages: every line is Lancaster's own or part of Node.js itself. Fewer moving parts means fewer places for a weakness to hide, and nothing to patch but Node.

Checked, then checked again

Every fix stays fixed.

ATLAS's security is tested in code, not just on paper. Each issue found in a review gets an automated test, and every update must pass them all before it is installed.

125Automated tests25 of them security tests: malformed requests, limits, sessions, access by role, escaping.

Security is never finished: reviews continue, and every update runs the full test suite before it is installed.
